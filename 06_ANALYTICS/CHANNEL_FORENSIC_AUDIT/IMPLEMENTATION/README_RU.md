# Рабочее исполнение recovery-плана

Поручение владельца от 2026-10-10: выполнить рекомендацию и закоммитить. Это рабочее продолжение аудита; исходные наблюдения остаются историческими. Бренд, ниша, Harrison, фактическая точность и порядок Valve → Waymo сохраняются.

- [Реестр измерений](MEASUREMENTS.csv): перенесены 29 реальных исторических наблюдений, 3 longform и 26 Shorts. Они не названы T24/T48 задним числом.

- [Проверка реестров](validate_tracking.py) и [результат](validation_result.json).

## Как работать
1. Перед продолжением читать актуальный manifest/STATE выпуска и текущие receipts. Не повторять уже выполненное скачивание или оплаченные jobs.
2. После реального Studio-экспорта добавлять строку MEASUREMENTS.csv: отдельные дата сбора и диапазон отчёта, тип контента, источник, версия упаковки, ограничения. Не затирать baseline.
3. Для T24/T48/T72/T7 обязательны точные publication_at и captured_at с часовым поясом. OBSERVATIONAL означает неподходящий для одинакового возраста срез. Пустое поле — неизвестно; 0 — измеренный ноль.
4. source CTR записывать отдельно по источникам. Не заменять Shorts stayed отношением engaged/views и не смешивать overall views с impression funnel.
5. В QC ставить PASS только для конкретного проверенного артефакта, с SHA-256, свидетельством, датой и reviewer. Технический PASS не закрывает слуховой/творческий/юридический QC.
6. В task board DONE требует evidence. Эксперимент RUNNING требует фактический start_at и зафиксированные control/variant, не просто подготовленный brief.
7. Запуск проверки: python 06_ANALYTICS/CHANNEL_FORENSIC_AUDIT/IMPLEMENTATION/validate_tracking.py. Она проверяет записи, а не качество фильма и не статистическую значимость.

## Порядок действий
Первые 48 часов: выгрузки → актуальные release receipts → слуховой QC 004 и настоящий Resolve canary → точечная проверка хвостов eBay/DK → фиксация текущих A/B.
До 14 дней: подготовка первых секунд 004/005 и нового короткого формата по существующему <=30s lock; один фактор за раз.
До 30 дней: сопоставимые окна по источникам, часы/затраты, решение по устойчивой частоте и следующей теме.

Предложение 1/week → условно 2/week используется для оценки ресурсов. Оно не переносит действующие публикации: у проекта остаётся ранее заданный every-two-day calendar, пока отдельно не внесено конкретное изменение дат. Ни один hard gate не обходится ради календаря.

## Границы выполненного
Система учёта внедрена в Git. Новые exports, слуховая проверка, Resolve import, публикации и живые A/B не выдаются за выполненные. Канонические сценарии и платформенные настройки не менялись. Paid generation не разрешена этим рабочим планом; требует отдельного точного quote/job approval по AGENTS.md.
